# Pytest 测试函数编写约定

为本项目新增或修改测试时，始终优先写简单的模块级测试函数，让读者能快速看懂测试目标和执行步骤。

## 必须遵守

1. 默认使用模块级 `def test_...` 函数，不使用测试类。只有确实需要 Pytest 的类级 fixture 或类级行为时才使用 class，并保持必要性明确。
2. 每个测试函数都要有简短中文 docstring，直接说明该函数验证什么。
3. 测试体按执行顺序写清楚步骤。每个有意义的测试步骤前，使用中文注释并按 `Step 1`、`Step 2` 顺序编号；注释要具体说明这一步做什么，读者不看实现也能理解测试意图。
4. 注释使用 UTF-8 编码的中文，内容简短且必要。不要给显而易见的赋值、断言或每一行代码重复加注释。
5. 保持测试函数最简：只保留该场景所需的准备、操作和断言；优先复用现有 fixture、`flows/` 和 `devices/` 能力，不在测试里复制驱动实现。
6. 测试表达业务行为和结果断言，不把无关逻辑、通用 helper 或复杂设备操作塞进测试函数。
7. 真实设备用例必须标记 `@pytest.mark.device`；依赖 AI 服务的用例按项目约定标记 `@pytest.mark.ai`。不能把设备未连接或服务未配置报告成测试通过。
8. 使用有意义且具体的断言。只有在项目既有设计明确要求时才跳过用例；不要捕获并吞掉意外异常。
9. 不在测试、注释或测试数据中写入 API Key、密码、Token 或真实敏感数据。
10. 保持 UTF-8 编码和现有 Python 风格；新增类型标注时保持简洁，不为简单测试引入多余抽象。

## 推荐结构

```python
import pytest


def test_example_behavior(example_fixture):
    """验证示例行为符合预期。"""
    # Step 1：准备并读取本场景需要验证的状态。
    state = example_fixture.get_state()

    # Step 2：执行目标操作并确认结果符合预期。
    result = example_fixture.perform_action()
    assert result == state.expected_result
```

示例中的 fixture、方法和结果仅用于说明结构。编写实际用例时，应替换为项目里已经存在的能力和真实业务断言。

## 完成前检查

- 测试是否为模块级函数；如用了 class，是否有明确的 Pytest 需求？
- 函数 docstring 是否用中文准确说明了测试目标？
- 每个有意义的测试步骤是否有按顺序编号的中文注释，并说明这一步做什么？
- 是否只保留必要的步骤、注释和断言？
- 设备或 AI 用例是否带正确 marker，且没有把依赖缺失伪装成通过？
- 文件是否为 UTF-8，是否遵守 `AGENTS.md` 中的目录职责和依赖方向？
