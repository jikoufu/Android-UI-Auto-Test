# 代码实现

读取当前任务需求、适用设计与项目政策，先定位现有实现和调用方。围绕验收条件完成最小完整变更，保留无关用户修改。

对适合 TDD 的变更，沿用已有先行测试和 Red 证据，确认失败对应目标行为后，用最小完整实现使测试通过。通过后只整理本次触及的代码，并复跑相关检查。仅在重复代码实现同一条规则且需要同步变更时合并，避免为了形式相似引入抽象。

更新受影响的调用方、配置和使用说明，避免通过第二份配置或隐藏兼容层掩盖迁移遗漏。底层操作、业务编排与接口层的归属以项目规则为准。

运行与变更相称的检查，并将命令、退出码、行为结果与未验证条件交给验证阶段。实现者自测不等于独立验证；缺少依赖时记录阻碍，不能伪造通过结果。

## dev-workflow

用户手动进入 Development 后，用只读的 `development-input` 读取批准需求、设计、测试方案和执行证据。核对归档 Red 对应的目标行为后，只在返回的 `worktree_path` 编辑业务代码和运行命令。保留已批准测试、夹具、配置和输入。工作区或任务版本过期时重新读取状态。

复核 Red 对应目标行为。原本已通过的用例，先判断现有实现是否足够；测试错误、缺失证据或验证输入变化交回 Test Design。纯人工或环境依赖的用例只沿用批准计划中的替代验证，记录实际执行结果和限制。

先复用现有项目代码、标准库和框架能力，只实现批准范围内的最小完整变更。确需新增抽象或配置时说明现有能力缺口。每完成一个可验证单元就运行相关测试。Green 后只整理本次变更，保持现有契约和兼容性，重新运行相关检查。真实 TV、ADB、外部服务和项目设备测试需要用户授权。

在 `development_path` 写 `## Summary`、`## Trace` 和 `## Verification`。追踪每个已批准 FR/AC，格式为 `- FR-001 / AC-001: 模块或符号及验证证据`。验证记录包含实际命令、结果、未执行项及原因。运行批准的离线节点以及适用的项目回归，再按共享 Workflow 提交给用户批准。阶段和批准由编排器写入。
