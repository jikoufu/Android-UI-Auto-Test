# 架构设计

## dev-workflow

仅处理手动启动的 `dev-workflow` 已授权的 Design 阶段。收到 `design/running` 后，由编排器执行 `design-input`。使用其输出的 `approved_requirements` 作为需求输入。可变的 `requirements.md` 和未经编排器验证的文件都不能作为批准依据。

在返回的 `worktree_path` 内读取适用的 `AGENTS.md`，检查现有模块、函数调用、API、数据模型、存储、依赖和测试。引用实际路径和符号，区分现状、计划改动和待确认假设。仅编辑返回的 `design_path`。继续时先检查已有草稿与当前批准版本的关系，复用仍适用的内容。

在 `docs/changes/<task_id>/design.md` 使用 UTF-8 Markdown 和以下二级标题。按复杂度选择必要设计，API、模型、接口及非功能设计按需添加。

| 标题 | 内容 |
| --- | --- |
| 文档元数据 | 每行一个 `- key: value`，填写编排器返回的 `task_id`、`requirements_sha256`、`requirements_approval_id` 和正整数 `design_version`。修订草稿时更新设计版本。 |
| 设计目标与非目标 | 对应已批准范围，列出明确排除项 |
| 当前系统架构及相关实现 | 实际路径、符号、调用链、数据和现有测试证据 |
| 受影响模块与变更范围 | 修改与新增模块、公共接口、存储及兼容影响 |
| 方案概述 | 模块职责和边界，复用已有能力 |
| 关键业务流程 | 正常流程及主要调用顺序，必要时用图说明 |
| API、数据模型及接口设计 | 适用时记录契约、关键组件和数据约束 |
| 异常处理与边界条件 | 错误响应、边界、权限和数据安全 |
| 非功能设计 | 适用时说明并发、锁、事务、性能或资源约束 |
| 兼容性与风险 | 现有调用方、迁移、回滚、风险和假设 |
| FR 与技术设计的追踪矩阵 | 每个批准的 FR 一行，填写模块、接口或组件、设计说明三列 |
| 技术决策 | 对重要选择说明背景、备选项、取舍理由及限制 |
| 待确认问题 | 技术阻塞用 `- Q-001 具体问题`，已批准需求有重大缺陷用 `- RQ-001 缺陷及需确认的改动`。全部解决后正文仅写 `无`。 |
| 下一阶段测试设计的输入约定 | 可测边界、环境、夹具、验收证据和未验证前提 |

追踪条目格式为 `- FR-001: 模块 | 接口或组件 | 设计说明`。

存在 `RQ` 问题时保存草稿并提交，解释为什么必须重新确认需求。等待用户另行手动调用 `revise-requirements`。在该阶段保留已批准的需求快照和原需求文档。没有阻塞时提交设计并展示方案摘要、关键取舍、风险及版本确认命令。Design 阶段不实施代码或测试，也不直接修改任务状态。

## 既有 Harness YAML 人工流程

读取当前任务需求与项目政策，检查现有调用方和配置入口。在 `design.md` 记录本次需要改变的模块、接口、依赖方向和兼容方式。

优先复用已存在的边界；新抽象须解决当前具体问题。结构迁移要同时覆盖导入、资源定位、启动命令、测试收集和文档。识别需保留的数据与现有未提交变更。

为每条验收条件给出验证方法与所需环境。只把已经实现且检查过的能力标为可用；未来目录和接口明确说明尚未实现。设计不得自行扩大用户授权的发布或外部操作范围。
