# 需求分析

`dev-workflow` 中的 Requirements 只能从手动工作流进入。收到 `requirements/running` 的任务信息后，在返回的 `worktree_path` 内开展需求分析，读该检出的 `AGENTS.md` 和适用的项目资料。使用返回的 `requirements_path` 写入或更新 `docs/changes/<task_id>/requirements.md`。继续任务时先读已有草稿，保留已确认的内容和仍适用的编号。

梳理用户原始需求、业务目标、角色和场景。检查涉及的代码、接口、数据结构和实际行为，引用 Worktree 内的相对文件路径及必要的符号名，区分观察到的行为与拟议变更。明确范围、非目标、兼容性、业务规则、正常与异常流程、边界和风险。对尚无依据的关键业务规则提出具体问题，记录各选项会改变的行为。

按 [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html) 的需求工程原则编写清晰、可验证、可追踪的条目。每个功能需求描述单一可观察行为。每个验收标准写明适用前提、操作及预期结果，标出需要真实设备或服务的验证条件。按任务复杂度控制篇幅，适用时补充非功能需求。

使用 UTF-8 Markdown 和以下二级标题。按实际情况组织正文。

| 标题 | 内容 |
| --- | --- |
| 需求背景与业务目标 | 原始诉求、原因、期望成果 |
| 当前系统行为 | 调查发现和代码证据 |
| 需求范围与非目标 | 改动边界、明确排除项和兼容性 |
| 角色及业务场景 | 参与者、触发条件、正常流程 |
| 功能需求 | 使用 `- FR-001 描述` 格式的唯一编号 |
| 业务规则与约束 | 已知规则、兼容性、风险和假设 |
| 异常及边界场景 | 异常输入、失败路径、边界及预期响应 |
| 非功能需求 | 仅在适用时添加 |
| 验收标准 | 使用 `- AC-001 描述` 格式的唯一编号 |
| 待确认问题 | 有问题时逐条列出，例如 `- Q-001 具体问题`。全部解决后正文仅写 `无` |
| 需求与验收标准追踪关系 | 每个 FR 一行，例如 `- FR-001: AC-001, AC-002`。覆盖全部已定义的 FR 和 AC |

FR、AC 和追踪章节使用上述列表格式。编号从 `001` 开始，条目需有正文，且每条 FR 对应至少一条明确的验收标准。同一条追踪记录内不可重复引用 AC。将附加示例和代码块放在其他章节。

存在重大歧义时先保存草稿并交给编排器 `submit`，进入 `waiting_for_input` 后提出具体问题并等待。问题解决后更新同一文档。提交无待确认问题的完整草稿后，向用户展示需求摘要、验收标准和对应版本的确认命令，并等待用户另行调用。Requirements 只负责分析和文档，所有状态更新由编排器执行。

既有 Harness YAML 人工流程沿用其 `requirement.md` 输出约定。该流程按自身任务协议记录范围、依据、验收条件和待确认事项。
